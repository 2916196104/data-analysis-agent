# 使用只读评论分析 Agent

评论 Agent 复用 HelloAgents 和现有评论统计函数，根据问题选择工具，返回统计、商品对比和原文证据。它使用已有标注；需要先准备评论数据和至少一个标注版本。

## 在工作台提问

1. 按原方式运行 `python run.py`，在工作台选择数据集、商品、分析时间和标注版本。
2. 打开“AI 助手”，选择“评论分析”，在输入框上方确认数据集、版本、商品及当前/基线时间，再填写问题。
3. 点击“提交问题”。后端读取已有 `.env` 的模型配置，通过持久化任务队列执行。
4. 查看分析结论、对应结果表格、原文证据和工具执行记录。点击“查看原文”可以查看完整评论、观点、原文位置和人工/模型来源。
5. 刷新或从“任务记录”重新打开结果；恢复结果不会再次调用模型。“导出分析报告”下载 Markdown，包含固定范围、标注与执行模型身份、统计表、来源与完整结果附录；原“下载 Agent JSON”保留。切换数据集不影响历史报告。

问题示例：

- 按日查看评论数量和负面评论数量的趋势。
- 对比所选商品的负面评论占比，并展示包装负面评论的原文证据。
- 查看六个维度的问题数量及较基线的变化。
- 当前范围缺失正文多少条？哪些标注失败，覆盖率是多少？
- 按月份查看包装、物流负面问题的变化，并保留覆盖率。
- 比较所选商品的 1–5 星分布，再按月查看星级分布。
- 比较当前窗口和基线；或在已选范围内比较 2023-02-10 至 2023-02-20 与 2023-01-05 至 2023-01-15。

商品和日期范围由页面绑定。窗口对比可从问题中提取更小的日期窗口，每个窗口须完整落在已选当前或基线范围内，且基线早于当前；不会扩大日期或跨越两个已选范围之间的空隙。需要其他范围时先“切换范围”。Agent 模型使用后端的 `LLM_MODEL_ID`、`LLM_BASE_URL` 和 `LLM_API_KEY`；“标注版本”决定查询哪一套已有观点，两者可以使用不同模型。

## 多轮追问与澄清

### 逐商品分析优缺点

可提问“美的空调与小米空调的优缺点都有哪些？”、“A 与 B 的优点和缺点”或“这款商品的好评和差评主要说什么”。本轮最多分析两个明确的品牌/商品组。

问题中的商品 ID、完整名称，或在当前数据集中唯一匹配的品牌/品类简称，优先于页面单款选择。例如页面仅选择 A，但问题明确询问 A 与 B 时，执行范围会冻结为这两款；成功回答的范围栏、查询快照下载和历史读取都保留实际商品范围。“美的空调”“小米空调”等明确品牌与品类会按目录中的品牌字段归组，包含当前数据集该组匹配的全部型号，并显示型号数；不会把品牌问题任意缩成一款型号。不会跨数据集查找；未找到另一款或具体系列简称对应多个型号时，直接说明缺少哪个商品及需要的 ID，不执行单款替代比较。

应用将查询拆成每个商品组的正向、负向观点原文归组，直接使用原只读注册表、调用预算和结果校验，不调用规划或回答模型。两个组执行四项观点查询及一次范围读取。每个组和方向展示最多两种出现较多的原文表述、评论数和观点数，同时保留各组样本量、成功标注数、覆盖率及可追溯引用。占比分母是该组包含对应情感观点的匹配评论数，不能当作全部评论中的好评率或差评率；同义表述没有合并为完整主题排名。品牌结果仅描述该数据集覆盖的型号和样本，不能外推整个品牌。

没有匹配负面观点不表示“没有缺点”，未标注、失败和无评论也不能解释为真实零值。任一必需查询或统计/原文校验失败，仍禁止发布成功回答。双向趋势、多个细分主题、指定双向原文条数/分页需分别查询，不会静默改成单向统计。

此路径使用 `review-agent-v7` 执行版本。更新代码后需重启后端及任务 worker，再提交新问题；历史失败任务不会被改写为成功。原 API 路由、任务请求字段、数据库结构和既有统计口径不变。

隔离验收：`python -m unittest discover -s tests -p test_assistant_semantics.py -v`；完整前后端链路：`node frontend/tests/pros-cons.e2e.mjs`。后者启动临时 SQLite、现有 API/worker、Vite 和 Chromium，模型端点只计数并返回错误，要求零模型请求；截图和检查记录保存在 `output/playwright/pros-cons-*/`。这些模拟商品评论不代表真实品牌结论。

在“评论分析”模式完成查询后，可以继续输入：

- “只看物流”：承接上轮趋势或原文的商品筛选，仅切换维度；原文从第一页重新查询。
- “换成按月”：承接上轮趋势的维度和商品，改为按月；星级分布也支持按月。“改成按日”适用于趋势。
- “继续查原文”：维度趋势转为同维度的负面原文；上轮已有原文时保留商品、维度、情感、当前/基线窗口和每页数量，查询下一页。到末页后提示调整范围。

追问只承接成功任务的实际工具参数。缺少成功上文、不支持的转换、含糊指代、多个查询目标或页面范围与上轮不同，都先显示澄清。可点击明确的范围/目标选项，或输入完整问题。澄清期间不会创建分析任务或调用模型。打开历史任务后追问，以当前查看的轮次为起点；不会跳过失败轮次去猜测更早的查询。

每轮显示“查看本轮查询快照”，保存原始问题、解析后的完整查询、固定范围、记录时间和父轮任务 ID；可下载 JSON，已完成轮次还包含服务端执行时间及实际工具结果。后续修改范围或失败重试不会改写旧轮。澄清与分析请求快照保存在当前浏览器 localStorage，刷新恢复不自动重发；服务端仍通过已有任务保存执行结果。清除浏览器记录后可从任务历史找回已执行查询，但本机澄清记录和父轮关联无法跨设备恢复。

实现沿用原任务 API：前端仍用确定规则处理明确追问与分页，未命中的口语也携带 `context_task_id`，由后端补全意图。后端最多读取 4 轮关联任务；失败轮次只恢复用户明确要求，成功结果必须再次通过数值与范围校验，才可提供查询条件和结果引用。基础问答仍是单轮模式。

### 结构化语义与下钻（第一阶段）

- “美的空调好评主要集中在哪些方面？”之后问“使用效果主要集中在哪些地方？”，继承商品、正向情感和窗口，查询 `get_opinion_breakdown(aspect=effectiveness, sentiment=positive)`，不要求重新选择商品。
- “美的空调的好评主要是什么？”保持正向维度汇总；“那物流方面呢？”保留适用的汇总、观点细分或原文目标。上轮有多个不同目标且无法唯一确定时，会具体询问继续哪一类。
- 比较任务失败后，“对比这两款商品的差别”可以恢复原请求里的明确商品名称。品牌有多个型号时列出候选 ID，要求选择具体商品；已在页面明确选择两款时可直接比较。失败任务的统计和原文不会作为可信数据继承。
- 不存在的商品直接说明无法在当前数据集中匹配；不会用页面默认商品替代。当前问题明确指定的商品优先于历史和模型输出。

`Conversation.intent` 只保存最近用户请求与任务引用，`Conversation.context` 保留最近成功且已校验的查询条件；二者分别持久化，普通聊天消息不进入分析上下文。服务端以任务记录重新校验，不信任浏览器提供的统计。

规则未命中时，`AGENT_SEMANTIC_PARSING=rules_then_llm`（默认）允许使用配置模型解析一次意图。设为 `rules_only` 可关闭此补充调用；规则与有限上下文补全仍然保留。模型只接收当前问题、精简意图条件、最多 4 项查询条件及 JSON Schema，输入最多 16,000 UTF-8 字节，不发送评论、统计或完整历史。单次请求沿用配置超时、最高 30 秒，SDK 自动重试为 0。

意图包含查询类型、用户商品表述、情感、一级维度、下钻/原文目标、主题、时间范围及澄清标记。后端验证实体来源、维度、日期及类型兼容后，编译为现有 `ReviewQueryPlan`，再通过原注册表、参数校验和结果校验执行。模型不能返回 SQL、新数据集或新标注身份。复制已冻结的日期属于继承；其他日期必须明确出现在用户问题中且不越出绑定窗口。

任务结果增加可选的 `user_intent`、`intent_resolution`、`intent_model_calls`；原 `model_calls` 仍指规划模型，`total_model_calls` 现在包含语义解析。模型解析超时或 JSON 结构失败时，任务明确失败且不执行统计查询，不伪装成用户信息缺失。

本阶段执行版本为 `review-agent-v8`，更新后需重启后端与 Worker，提交新任务。未新增路由、必填请求字段或数据库迁移。现有无上下文任务和历史结果继续可读；超过有限历史链、尚无工具支持的统计，以及口语分类一致性，仍需后续评测。

## 结果如何生成

模型负责选择工具、修正工具参数和返回结果 ID。代码核对实际结果引用，并把统计数字和原文片段整理成中文回答；首版不生成自由发挥的原因解释。

| 工具 | 能力 |
| --- | --- |
| `get_analysis_context` | 已选范围、商品 ID、标注覆盖率、维度和情感枚举；执行前自动读取一次 |
| `get_trend` | 当前窗口按 UTC 日/月统计整体评论趋势 |
| `compare_products` | 当前窗口的商品数量、覆盖率和负面占比对比 |
| `get_top_issues` | 六维度问题数量、占比和基线变化 |
| `get_evidence` | 按商品子集、维度、情感和当前/基线窗口分页查询原文证据 |
| `get_data_quality` | 当前/基线范围的缺失正文、成功/失败/待标注、失败类型、覆盖率及导入文件指纹 |
| `get_aspect_trend` | 按日/月查询指定或全部六维度的去重负面评论数与占比，保留各桶分母和覆盖率 |
| `get_rating_distribution` | 按商品、月份或总体查询原始星级；可选当前/基线窗口 |
| `compare_time_windows` | 比较已选或缩小后的两个窗口，输出计数变化、覆盖率/负面占比百分点变化及六维度对比 |

所有工具共用一条只读事务，读取同一数据库快照，并使用既有的去重、统计分母和最新人工复核规则。`as_of` 沿用现有业务口径，仅筛选评论发布时间，不表示重建历史时刻的人工复核状态。

空分母不转成 0。工作台把成功标注数直接列为“分母”，同时展示负面数/成功标注数和成功标注数/有效正文数；成功数为 0 时按“待标注”“标注失败”“无有效正文”或“无评论”说明原因。已有成功标注但负面数为 0 时仍显示真实的 `0.0%`。商品对比支持搜索和状态筛选，历史结果也会按表格重新排版，不再把所有商品拼成一段长文本。

星级分布独立于标注：直接读取原始 `rating`，有效整数星级为 1、2、3、4、5；缺失与非整数/其他评分单独计数，不四舍五入，也不使用情感推断。星级占比分母为有效整数星级评论数。数据质量的缺失正文率以全部评论为分母，失败率以有效正文为分母。维度趋势按评论去重，多条同维度负面观点只计一次；空月份保留空分母。时间窗口允许不同长度，但报告会同时显示天数，不能只凭总数量判断恶化。

“准备待处理商品”只打开现有标注表单，不会自动调用模型。入口会带入 Agent 结果的数据集、商品、UTC 日期和截止时间，用户明确提交后才创建标注任务；完成后需要用新标注版本重新分析。原文证据在页面中以引用卡片展示，完整文本、哈希和行号仍可从详情或 JSON 下载查看。

成功回答会附带确定性校验记录：计数关系、负面占比和覆盖率分母、原文引用位置，以及最终结果 ID 是否覆盖所有已完成查询。任一校验失败时任务不会标记为成功回答。

## 接口与任务兼容

继续使用 `POST /api/v1/tasks` 的 `kind="analysis"`，在已有分析参数中增加可选的 `question`。省略 `question` 仍执行原结构化分析，不调用问答模型，原任务载荷的幂等哈希保持不变。

提交 Agent 任务时必须明确 `source` 和 `dataset_version`，同时保留原有商品、日期、基线和标注身份字段。客户端不能传入 `model_identity`；服务端自动冻结执行模型和 `review-agent-v2` 提示词版本。执行前或重试时发现模型身份变化，会要求重新提交任务；已完成的 v1 历史结果仍可读取和导出。

第三阶段增加四个只读 GET 端点，原端点不变：`/api/v1/analytics/data-quality`、`/api/v1/analytics/aspect-trend`、`/api/v1/analytics/rating-distribution`、`/api/v1/analytics/compare-windows`。前三者使用现有分析身份与范围参数；维度趋势可带 `aspect`、`period`，评分分布可带 `group_by=product|month|all`；窗口比较还须带 `baseline_from`、`baseline_to`。HTTP 调用方可以自行指定范围，Agent 层额外强制检查本次冻结范围。

Agent 结果直接保存在任务的 `result` 中：

- `agent=true`：标识问答结果，前端不再请求 `/analysis-runs/{run_id}`。
- `status`：`ok`、`unsupported` 或 `error`。错误对应任务 `failed`；能力或范围不支持时正常保存说明。
- `scope`、`snapshot_at`：已校验的查询范围和查询开始时间。
- `answer`、`result_ids`、`results`：由实际工具结果整理的回答及结果引用。
- `validation`：代码生成的数字、分母、引用和结果覆盖校验；`status=passed` 才允许发布成功回答。
- `trace`、`usage`、`model_calls`、`tool_calls`：模型用量、工具记录和调用次数。
- `warnings`：分母、样本量及证据解释限制。

只读指业务库：Agent 不写评论、观点、人工复核、分析运行或告警表。任务队列仍保存提交状态和执行结果，无需新增数据库表或迁移。

## 首版边界与错误处理

- 模型服务须支持原生工具调用。现有 `AGENT_MAX_STEPS`、`AGENT_MAX_TOOL_CALLS`、`LLM_TIMEOUT_SECONDS` 和 `LLM_MAX_RETRIES` 继续生效；自动读取上下文也计入工具调用次数。
- 工具仅接受声明的参数；数据库路径、来源和标注版本不能改写，商品子集和自定义窗口不能越出已选范围。
- 相同工具与相同规范化参数复用本次结果。最终 JSON 格式最多纠正一次，仍受原调用预算限制。
- 未解决的工具失败、虚构结果 ID、遗漏已完成结果和耗尽预算都不会宣称分析成功。
- 最多选择 100 款商品；趋势最多 366 天或 240 个月；证据默认每页 5 条，最多 10 条。需要更多证据时可在问题中要求查询其他页，但仍受调用预算限制。
- 服务端每个任务独立执行只读问答；前端支持上述分析追问与澄清，不自动标注或执行任意 SQL/代码。原“开始分析”入口继续执行固定分析与规则检查。
