# P5：问答能力与语义覆盖差距

2026-11-06。**当前主要瓶颈是查询目标解析和证据语义覆盖；真实 RAG 基础链路不需要重建。** 本轮检查 P4 报告及实际源码，执行 15 个自然语言合成探针、147 项现有回归；未连接真实 PostgreSQL、加载真实 Embedding 或调用外部模型。没有修改业务逻辑、R0、人工参考、索引或 `.env`。

## 当前能力分界

| 类型 | 当前能力与边界 |
|---|---|
| SQL 确定性统计 | 正负维度计数/占比、评论量、数据质量、星级分布、负面维度趋势、商品/窗口对比。分母依赖各工具定义及标注覆盖，不依赖 200 条向量 |
| SQL 观点/原文 | `get_opinion_breakdown` 按观点文本归组，`get_evidence` 按维度、情感和时间分页；细分主题文本匹配不等于语义分类 |
| RAG 证据检索 | 原问题 → BGE-M3 → 单商品 Top-5 → 来源核验 → `reported_experience_v2` → 许可引文与模板回答。完整评论只解释或否决 quote |
| 模型依赖路径 | `get_aspect_drilldown` 的主题归并、部分意图兜底/Agent 调度、复杂统计解释可能调用已有外部模型；不能把“SQL 算数字”说成“所有 SQL 问答都零模型” |
| 尚不可靠支持 | 任意语义改写、任一/多分支条件、时间先后、纠正焦点、长期自述的广泛表达、因果证明、细分语义主题的总体比例；应澄清或明确能力不足 |

受控事实语法可识别制冷/制热表现、速度、噪音、配送、客服与安装角色、包装和价格的部分完整表达，并有“完全失效 → 效果不佳”的显式蕴含。它证明的是**存在该买家自述**，不证明客观性能、总体发生率或故障原因。P4 已实际证明制冷不足正例和 SQL 正向统计可用；未证明通用语义理解。

## 15 个问题与实际合成结果

范围沿用已有临时 SQLite/FakeEncoder/FakeRepository/FakeAgent 框架，商品为合成 P1，日期为 2023-01-01—06。候选由开发者明确提供，**不是 BGE 真实召回，不据此计算检索准确率或泛化成绩**。FakeAgent 只执行原计划，不替生产路由决定问题含义。

|---|---|---|---|

## 五类差距与真实证据的区分

1. **路由/理解**：P05、P10 已复现；P12 的任务类型也偏离。`review_semantics._pros_cons_products()` 将疑问修饰语留在商品名中；`review_plan` 的 `评论.*多少` 将细分比例误判为质量查询；原因问法可能降为文本主题匹配。优先修这些共性边界，不给单题增加特例。
2. **检索覆盖**：P3-B 保存观察为 200 条向量、1091 条有效观点，约 18.3% 的观点有向量；不是 18.3% 的评论覆盖率，更不是 Recall。单一问题向量 Top-5 也可能遗漏复合条件中的另一事实。没有对余下观点做完整相关性判断，**不能指定 P02/P08/P13 的真实失败就是索引缺失**，也不能擅自扩索引。
3. **证据判断**：`target()` 对整句做固定格式匹配，`fact()` 只接受受控完整子句；P02/P03/P06/P08/P11/P13 因此 unknown。`context_ok()` 全文扫描转折、转述等词，可能把无关上下文也作为否决。P3-A 实际候选中带短期使用修饰的故障自述曾未被识别，这是已见真实规则覆盖缺口；真实十年问题则同时存在“规则未覆盖”和“该次候选未证明长期使用”，两者不能混为错误拒答。
4. **回答**：语义回答只复述许可引文，正常路径未见新造事实；但 `task.status=ok`/结构校验通过不代表答到了问题。P10 输出真实统计却回答了别的问题。当前 v2 只产生 sufficient/insufficient，不产生 limited，独立子问题可能被一并拒答；不同 unknown 的前端提示也较接近。
5. **性能**：本轮合成耗时不代表业务时延。已有 P4 实测前端首次约 14.1 秒、连续问题约 2.1–5.4 秒；与 P3-B 直接调用热请求中位数 0.570 秒口径不同。尚无理由重做向量存储或 ANN 索引；新增模型判断会增加延迟和成本。

## 是否需要 LLM 结构化证据判断

**值得做可关闭的小范围试验，但应先修查询契约；不能将 LLM 自由回答接到候选之后。** 继续堆完整句式无法覆盖普通改写和复杂上下文。第一版宜只处理“目标已明确、候选支持关系未知”的问题；目标自身不确定时先澄清，不让一次模型同时改写问题又自证支持。

最小设计如下，均为建议，尚未实施或测量：

- **输入**：原问题、已确定的目标事实 ID/描述、对象/子主题、all_of/any_of、独立子问题和必要关系；不可变 scope/请求摘要；仅本次 Top-K 的来源键、review_id、quote/精确区间及对应完整评论。完整评论只做限定/否决。不得传人工参考、相关性分数或把相似度作充分性概率。
- **输出**：严格 JSON，逐 fact 返回 `direct_report / contradicted / unknown`、依据、引用键和支持子区间；逐关系返回 supported/unknown/contradicted 及所涉事实/来源；另列上下文否决引用。不能自行返回新统计或改写来源身份。
- **后端许可**：来源校验继续先行；支持区间必须完全落在当前候选 quote 内并精确切片。all_of/any_of、same_review 和 before 等必要关系由契约检查；before 不能只靠两段文字在文中的位置。只有显式可独立回答的子目标能进入 limited。统计仍走确定性口径；单评论不能证明总体比例或客观故障原因。
- **接入限制**：`validate_retrieval()` 会用 v2 重算 assessment，`semantic_answer()`/`validate_answer_bindings()` 也要求 v2 受控事实。**不能把新模型输出塞进旧 assessment，或关闭校验使它通过**。需独立版本的策略适配与结果验证，共享原来源检查；v2 和 R0 保留。现有 `QueryContract` 字段、枚举和纯校验可参考复用，但其冻结 run/manifest 的 scope_ref 不能用伪造值移植到运行时。离线 `evidence_judge` 也不等于现成的在线 LLM 判断器。
- **失败降级**：来源/范围错误作为执行失败；超时、非法 JSON、未知事实/关系保留 unknown，不自动放行、不自动重试。当前明确反证不升级；`context_unresolved` 不能一概当作可覆盖的软错误。保留规则正例，新增路径只处理其明确允许的未知分支。
- **预算**：可先建议每题至多 1 次证据模型调用、输入上限 8k token、输出上限 1.5k token、10 秒超时；这些是工程预算草案，不是质量验收门槛。若完整否决上下文超预算，不得静默截掉后放行，相关候选应 unknown。每次费用按 `(输入token×输入单价＋输出token×输出单价)/10^6` 计算；尚未选定/运行模型，不能报货币费用或实测延迟。若查询解析另需模型，要另计调用和时延。

结构和区间校验能阻止伪造来源，**不能独立证明自然语言蕴含正确**。后续应用合成正反例及另外准备的未见表达验证；不能只统计拒答安全性，还需统计有直接证据却被拒答和不当许可。当前 15 个已用于发现问题的探针不能再称为独立泛化集。不需要新审批平台；真实模型/数据运行仍按用户明确授权范围执行。

## 最值得实施的三个功能

1. **统一查询语义契约与任务完成检查。** 优先修通用商品指代/疑问修饰语、将日期/scope 与目标事实分开、区分事实存在/维度统计/细分主题比例/原因任务。保留原问题进入 Embedding；SQL 数字正确但任务不匹配时，不发布替代答案。复用现有意图解析、QueryContract 概念与 scope 校验，无需重构 Agent。
2. **未知分支的受约束证据判断。** 在新版本策略中试验单目标、逐事实 JSON 判断及局部上下文否决，保留原来源/引用校验、反例和规则回退。先证明能处理修饰表达及无关上下文，再考虑长期和时间关系；本轮不接外部服务。
3. **多目标分解与有限回答。** 先表示多个独立事实、任一/全部条件和同评论关系，明确哪些可单独回答；逐事实缺口明确展示，避免全拒答或跨评论拼接。以后若试验子查询召回，另设固定总候选预算、保留原排名并统一去重/校验；当前每轮一次语义查询的约束不能偷偷突破，也不自动扩大 200 条索引。
