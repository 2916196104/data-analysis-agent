# 商品数据分析 Agent｜AI 助手开发需求与架构设计

> **文档用途**：交付 Codex 作为开发依据。本文只描述当前对话已经形成的产品方向、第一版实施范围和约束；未明确的事项集中列在「待确认」。
>
> **文档状态**：第一版开发基线（以仓库现状核对为前提）  
> **适用项目**：商品数据分析 Agent  
> **已确认技术事实**：后端为 **Python + FastAPI**；**AI 助手前端聊天界面已经完成**；**目前尚不能完成 AI 问答**。

---

## 1. 产品定位与项目目标

### 1.1 产品定位

AI 助手是商品数据分析系统中的**统一自然语言分析入口**，不是脱离业务数据的通用聊天机器人。用户在已有的 AI 助手聊天页面提出问题，系统利用真实商品、评论、情感标注和问题分类数据，返回**可解释、可追溯、可继续追问**的答案。

### 1.2 第一版交付目标

在现有聊天界面中，让用户能够完成以下闭环：

1. 输入问题，获得真实大模型回答。
2. 针对当前商品及数据集，查询**评论总数**。
3. 查询**差评数量和差评率**等情感统计指标。
4. 询问**“差评集中在哪些问题？”**，获得问题分类、数量、占比及排序。
5. 查看主要负面问题对应的**原始评论证据**。
6. 基于当前会话进行连续追问，不必反复说明已确定的商品和分析范围。

上述是**第一版业务验收目标**。实现顺序见第 9 章；它不表示所有能力必须在同一次代码变更中上线。

### 1.3 不可违反的产品原则

- **真实数据优先**：大模型负责理解意图、决定是否调用工具和解释结果；统计数值由业务代码与数据库计算。
- **绝不编造**：未查询到的评论数量、比例、趋势、原始评论及数据来源不得虚构；数据不足必须说明。
- **统一入口**：通过已有 AI 助手聊天界面交互，不为每一种分析问题新建独立聊天页面。
- **复用已有能力**：尽量调用现有评论导入、标注、查询、统计与图表能力，避免重建平行业务系统。
- **先简单后复杂**：先接通问答，再接入数据工具；不因“Agent”名称而一次性引入所有框架。
- **证据与结论分离**：明确区分统计事实、来自评论的用户反馈、推测性原因和改进建议。

## 2. 当前状态与现有功能保护范围

### 2.1 已确认的现状

| 项目 | 已知状态 | Codex 处理要求 |
|---|---|---|

### 2.2 需要保留的已有功能与系统边界

在仓库中**实际存在**的功能、页面、路由和服务均须保留，尤其需要检查并保护：

- 数据管理与数据/文档导入功能。
- 评论标注、评论查询、数据分析与图表功能。
- 现有报告及其他已实现页面（包括此前讨论中提及的相关导航页面）。

**重要**：以上部分功能曾在讨论中被提及，但其**真实完成程度并未在本对话中逐项核实**。Codex 必须先阅读仓库，不能假定每项功能均已完整实现，也不能擅自重写。

### 2.3 本期修改边界

- 允许：为 AI 问答与商品分析增加必要的接口、服务、只读分析工具、会话数据与聊天消息展示能力。
- 禁止：未经需求明确要求而重做全站布局、替换既有评论处理流水线、修改无关业务模块或删除原有入口。
- 如果新需求依赖现有未完成能力：标记依赖或阻塞项，**不得通过伪造数据或暗中扩展范围来“完成”**。

## 3. 本期功能需求（第一版）

> 优先级说明：**P0** 为第一版核心业务闭环；**P1** 为对话体验与展示的配套能力。P1 可在 P0 基础链路跑通后完成，但属于本期第一版验收范围。

### FR-01｜基础 AI 对话（P0）

**用户目标**：在已有聊天页面输入普通问题并收到真实模型回答。

**预期行为**：发送消息后，前端请求 FastAPI 聊天接口；后端调用已配置的大模型，返回回答；聊天记录在页面中按用户/助手角色显示。

**实现约束**：
- 复用当前聊天 UI，模型调用只在后端执行。
- API 密钥不得出现在前端包或代码仓库中。
- 对模型不可用、超时、配置缺失等场景返回可理解的错误提示。
- 未接入业务查询工具时，模型不得声称已查到商品数据。

**验收标准**：
- 用户发送“你能做什么？”等问题，页面能展示模型生成的实际回答。
- 模型调用失败时有明确提示，页面不崩溃、不展示假答案。
- 前端网络请求中不包含模型 API 密钥。

### FR-02｜会话上下文与连续追问（P0）

**用户目标**：能连续讨论同一商品，无需每次重述背景。

**预期行为**：系统维护会话标识及必要的历史上下文；后续提问能够承接当前商品、数据集、时间范围和上一轮分析主题。

**实现约束**：
- 会话必须与当前用户/权限范围绑定；不可跨用户读取。
- 商品、数据集与时间筛选条件优先来自当前页面或用户明确指定的上下文。
- 上下文缺失或含糊时明确询问，不得擅自任选商品或日期。
- 会话持久化及具体生命周期规则见「待确认」；不得擅自引入 Redis 作为硬依赖。

**验收标准**：
- 用户先问“这款商品的差评率是多少”，再问“主要问题是什么”，第二问能够复用同一商品上下文。
- 切换商品或数据集后，回答不混入上一个商品的数据。
- 缺少必要商品上下文时，助手能够给出明确提示。

### FR-03｜商品基础数据查询（P0）

**用户目标**：例如询问“这款商品共有多少条评论？”

**预期行为**：Agent 识别统计查询意图，调用已有商品/评论数据查询服务，返回真实数值并说明分析对象和范围。

**实现约束**：
- 由后端执行确定性统计查询，模型不能自行编数字。
- 工具只允许查询用户有权限访问的数据。
- 复用现有数据库访问层与统计口径。

**验收标准**：
- 同一商品、数据集及时间范围下，助手返回的评论数量与后端统计查询一致。
- 没有匹配评论时如实返回 0 或“无数据”，而非编造数量。

### FR-04｜情感分布与差评率问答（P0）

**用户目标**：例如询问“差评有多少条？”“差评率是多少？”

**预期行为**：根据现有情感/评分数据获取相关统计，明确说明统计范围和采用的差评定义。

**实现约束**：
- 差评定义与系统已有评论标注或评分规则保持一致；具体判定口径尚待核实。
- 数据库完成数量及比例计算；统计时采用同一过滤条件与分母。
- 不得将“负面提及次数”混同于“差评条数”。

**验收标准**：
- 差评数、样本总数与差评率可通过业务查询复核。
- 无情感标签或数据不足时说明限制，不能用语言模型猜测情感比例。

### FR-05｜差评问题分布分析（P0，核心场景）

**用户目标**：询问**“差评集中在哪些问题？”**

**预期行为**：在确定商品和数据范围后，系统查询差评及其负面问题标签，统计各问题涉及的差评条数和占比，按提及条数降序展示，给出简明结论。

**实现约束**：
- 支持一条评论对应多个问题类别；**同一评论在同一类别下只计一次**。
- 仅将对应方面的**负面**观点计入负面问题；不将同一条差评中的正面方面算成问题。
- 计算并呈现问题标注覆盖率或明确说明存在未分类差评。
- 如果现有评论标注只有正/中/负、没有问题维度，**必须先列出依赖缺口及待确认的分类体系**；不得擅自创建任意业务类别作为确定规范。
- 问题的“出现频率”不等于“严重程度”；不得据此直接断言实际根因。

**验收标准**：
- 对含多标签、重复标签、未标注、无差评的测试数据，统计数值与预期完全一致。
- 输出至少包含：差评总数、各问题类别、提及差评数、占比、排序及数据范围。
- 没有可用问题标签时，不展示凭空生成的问题分布图。

### FR-06｜原始评论证据查询（P0）

**用户目标**：例如“展示几条关于商品质量的差评”。

**预期行为**：根据指定商品、范围和问题类别，查询相关原始评论；在回答中展示可辨识的评论内容与来源标识。

**实现约束**：
- 原始评论必须来自实际数据记录；保留用于追溯的评论 ID 或等价来源标识。
- 先实现按已有标签/条件的精确筛选；不要求本期实现 Embedding 语义检索。
- 遵循现有数据访问权限；不暴露无关个人信息。

**验收标准**：
- 展示的评论均能在当前数据集中按标识找到，内容与原文一致。
- 请求未命中的问题类别时提示“未找到相关评论”。
- 不出现来自其他商品或数据集的评论。

### FR-07｜流式回答与执行反馈（P1）

**用户目标**：知道请求已接收，并能看到回答逐步出现。

**预期行为**：前端可逐步展示模型回答；执行期间有明确加载/查询状态，出错时结束加载并给出反馈。

**实现约束**：
- 优先利用现有 FastAPI 和前端通信能力，讨论中的方案为 HTTP 流式传输/SSE。
- 不为实现流式效果而重建聊天界面或强制使用 WebSocket。

**验收标准**：
- 较长回答不是全部等待完成后才一次性出现。
- 请求失败或中断时加载状态能正确结束，已显示内容不会导致页面异常。

### FR-08｜结构化分析结果展示（P1）

**用户目标**：在聊天内容中直观看到主要负面问题分布，并查阅证据。

**预期行为**：对“差评集中在哪些问题”返回**摘要文字 + 分类指标 + 柱状图或现有等效图表 + 原始评论证据**。

**实现约束**：
- 复用已有图表组件、消息组件及页面样式；不要求 LLM 生成可执行前端代码。
- 图表数据由业务工具输出的结构化统计结果驱动，不能从模型自由发挥的文案中反向解析数字。
- 若无数据、缺少标签或统计失败，显示适当的空态/错误态。

**验收标准**：
- 图表数值与后端工具结果逐项一致。
- 一条评论属于多种问题类别时，前端不会错误暗示各类别占比之和必须为 100%。
- 当前 AI 助手页面的基本布局及其他导航功能保持不变。

## 4. 页面布局与交互要求

### 4.1 布局约束（已明确）

- **使用已有 AI 助手聊天界面**作为唯一问答入口。
- 在已有界面中显示用户消息、助手回复和分析结果；**不新建独立页面、不无关重构页面**。
- 原有导航、内容区及其他功能页面必须保持可用。
- 图表和评论证据应嵌入对话内容区，复用现有样式和组件。

> 对话中曾讨论“主内容区完整对话页”的方向，但**没有核验当前 UI 的具体布局结构、尺寸、侧栏行为**。Codex 必须以当前已有聊天界面为准；是否需要进一步调整主内容区/弹窗形式列入「待确认」，不得擅自改版。

### 4.2 用户主流程

**流程 A：普通对话**

用户输入普通问题 → 前端发送消息 → FastAPI 调用 LLM → 前端展示回复；异常时显示错误提示。

**流程 B：真实数据问答**

用户选择或当前页面已提供商品/数据集 → 提问评论数量或差评率 → Agent 选择受控查询工具 → 业务服务查询数据库 → 模型依据工具结果生成说明 → 页面展示结果。

**流程 C：差评问题分析**

用户提问“差评集中在哪些问题？” → 确认商品、数据集和适用的筛选范围 → 读取差评与方面级负面标签 → 统计并排序 → 获取典型原始评论 → 模型总结 → 消息内展示指标、图表和证据。

**流程 D：连续追问**

用户继续问“质量问题具体有哪些？” → 沿用同一商品/数据范围与上文问题类别 → 查询该问题相关评论或细分标注（仅当数据支持） → 给出有来源的回答；若没有细分标注则说明数据限制。

### 4.3 异常和边界状态

| 场景 | 必须表现 |
|---|---|
| 缺少商品或必要数据集 | 明确提示用户选择或确认，不能默认任选。 |
| 当前范围无评论 / 无差评 | 如实说明，无需生成虚假统计图。 |
| 已有差评，但没有问题标签 | 说明无法可靠计算问题分布；列出依赖。 |
| 只有少量有效样本 | 说明样本量及结论局限。 |
| 模型接口超时/失败 | 显示错误并允许用户重新发起请求；不得显示伪造完成结果。 |
| 用户无权访问目标商品 | 阻止查询及跨用户数据泄漏。 |
| 当前商品或筛选条件发生变化 | 更新查询上下文，避免混用旧数据。 |

## 5. 技术架构与职责划分

### 5.1 本期采用的架构方向

**已有聊天前端 → FastAPI Chat API → 对话/Agent 服务 → 模型客户端 + 受控 Tool Calling → 既有商品/评论业务服务 → 现有数据库及标注数据 → 返回结构化结果供前端展示。**

职责必须清晰分离：

| 层次 | 职责 | 约束 |
|---|---|---|
| 前端聊天 UI | 发送消息、承接商品上下文、渲染文本/结构化结果 | 复用已有页面，不持有模型密钥。 |
| FastAPI 接口层 | 请求验证、用户身份和权限、响应与错误处理、流式传输 | 沿用已有项目接口风格。 |
| 对话/Agent 服务 | 维护必要会话上下文、选择受控工具、合成回答 | 不能绕过业务校验。 |
| LLM 客户端 | 向已配置模型服务发送请求 | 模型厂商及具体 SDK 未确定。 |
| 分析 Tool 层 | 向 Agent 暴露少量明确定义的查询能力 | 参数受控，只读、可测试。 |
| 业务服务/数据层 | 评论统计、情感指标、问题分布、证据查询 | 优先复用现有逻辑和数据库访问层。 |

### 5.2 本期必须具备的工具能力

以下名称是**在对话中采用的候选命名**；若仓库已有等价服务或命名规范，优先复用。

| 工具能力（候选名） | 输入要素 | 返回要素 | 对应需求 |
|---|---|---|---|
| `get_product_overview` | 商品 ID、必要范围 | 商品基本信息、评论总数等 | FR-03 |
| `get_review_statistics` | 商品、数据集、时间范围 | 情感分布、差评数量、差评率 | FR-04 |
| `get_negative_issue_distribution` | 商品、数据集、时间范围 | 问题类别、数量、占比、覆盖率 | FR-05 |
| `get_issue_example_reviews` | 商品、问题类别、筛选范围 | 原始评论文本及来源 ID | FR-06 |

实现 Tool Calling 时，LLM 只能选择调用已注册工具；参数由后端解析、校验并执行。**不得开放任意 SQL 执行工具，不得允许模型直接修改业务数据。**

### 5.3 技术引入与实施顺序

1. **FastAPI + Pydantic + 已选大模型的 Python SDK**：基础聊天。
2. **会话上下文 + 流式传输**：可连续交互；优先复用现有数据库保存必要会话数据。
3. **Tool Calling + 现有查询服务**：真实商品指标问答。
4. **问题标签 + 确定性聚合统计**：差评问题分布。
5. **结构化消息展示**：图表和原始评论证据。

**非本期依赖**：Embedding、pgvector、RAG、LangGraph、MCP、为本功能新增 Redis 服务。

数据库在前文曾按 **PostgreSQL** 讨论，但**当前对话没有直接核验仓库数据库配置**。必须以实际项目为准；不得仅因本文示例而迁移数据库或替换 ORM。

## 6. 数据与统计口径

### 6.1 逻辑数据依赖（不是要求新建表）

| 数据对象 | 必要信息 | 用途 |
|---|---|---|
| 商品 | `product_id` | 唯一限定分析对象。 |
| 数据集/导入批次 | `dataset_id` 或项目现有等价标识 | 限定当前导入数据。 |
| 评论 | 评论 ID、原文、所属商品、适用的时间信息 | 评论总数、证据溯源。 |
| 评论情感 | 正面/中性/负面或项目现有评分体系 | 差评筛选、情感统计。 |
| 方面级标注 | 问题类别、该方面的情感极性、对应评论 ID | 问题分布、分类证据。 |
| 会话上下文 | 会话 ID、用户归属、当前商品/数据集/筛选范围 | 多轮问答与隔离。 |

字段仅描述逻辑依赖；**是否新建表、追加字段或复用现有 schema，必须先审查仓库后决定**。

### 6.2 差评问题分析的计算原则

设当前范围内差评总条数为 **N**，提及某一负面问题类别的**去重差评条数**为 **C**：

- **该问题提及占比** = C / N × 100%。
- **分类覆盖率** = 至少有一项可识别负面问题标签的差评条数 / N × 100%。
- 按 C 从高到低排序。
- 同一差评可计入多个不同问题类别，因此各类别占比之和**允许超过 100%**。
- N = 0 时不计算或展示具有误导性的百分比。
- 区分“差评条数”“问题类别的提及差评数”“全部评论数量”，不得混用。

**待确认**：何种评分/标签判定为差评、有效评论筛选规则、问题分类体系，以及默认时间范围。Codex 应先查现有逻辑，并将缺口记录为待确认，不能擅自定义新的业务事实。

### 6.3 回答的证据要求

- 统计结论需有对应的工具返回值。
- 引用评论需有真实评论 ID 或项目现有来源字段。
- 推测性原因必须使用“可能”“需要进一步核实”等表达，不伪装成已证实事实。
- 若缺少评论标注或来源数据，应明确解释能力边界。

## 9. 分阶段交付与验收门槛

### M1｜基础 AI 问答

- **交付**：现有聊天 UI 成功调用 FastAPI；后端成功调用已配置 LLM；页面正常显示回答及错误信息。
- **通过条件**：真实模型可回答基础问题；不暴露 API 密钥；不编造尚未接入的商品数据。
- **禁止扩展**：暂不接入 RAG、LangGraph、复杂工具编排。

### M2｜上下文与聊天体验

- **交付**：当前商品/数据集上下文传递、连续追问、流式展示、必要的会话记录支持。
- **通过条件**：同一会话追问能够承接上下文；切换商品后不串数据；流式输出与错误态可用。
- **条件**：会话持久化方式和历史记录具体交互待仓库核实；不得凭空重构已有会话管理。

### M3｜真实商品数据工具

- **交付**：受控工具可查询当前商品评论总数、差评数、差评率；Agent 根据工具结果回答。
- **通过条件**：与业务统计结果一致；无权限、缺商品、无数据均按预期处理。

### M4｜差评问题与证据

- **交付**：根据已有问题标注统计差评问题分布，返回排序、数量、占比、覆盖率及相关原始评论；聊天页展示结构化结果。
- **通过条件**：多标签去重正确、无标签不虚构、图表数字一致、评论来源可追踪。
- **阻塞条件**：若项目尚无可用问题分类标签，先报告依赖和待确认事项，不自行定义业务类目或伪造完成状态。

**实施原则**：每个里程碑完成后先测试与验收，再进入下一阶段；不要一次性修改整个前后端架构。

1. **先读仓库，后改代码**：先检查 FastAPI 入口、现有路由与服务、数据库/ORM、评论导入与标注逻辑、现有聊天 UI、依赖和测试。

4. 仅实现本期范围；任何新增页面、重构、数据库迁移、新依赖、问题类别体系等都要说明必要性。涉及第 10 章的未确认关键决策时，**暂停相关部分，列出待确认问题，不擅自定案**。

### 最终验收定义

第一版只有在以下条件均成立时才算完成：

- 现有 AI 助手页面可以正常问答和连续追问。

- 对“差评集中在哪些问题？”能够输出**有真实依据**的问题分布，而不是通用推测。
- 能展示对应的原始评论证据和数据范围；图表/指标与业务统计一致。
- 不破坏仓库中的现有功能；未确认、未完成和受依赖阻塞的部分均被明确记录。
